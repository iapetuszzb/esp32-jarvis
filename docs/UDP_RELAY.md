# 热点内 TCP / UDP 摄像头中转（v0.2.0）

## 数据路径

ESP32-S3 → 手机热点内加密 TCP（优先）/ UDP（兼容回退）→ Android 摄像头中转服务 → HTTPS → 现有云端 API。音频继续使用 App 与服务器之间的 WSS。当前 trycloudflare HTTPS 入口不能直接接收自定义裸 UDP；这里的 TCP / UDP 均只在热点局域网使用。

这样把 ESP32 的公网 TLS 握手交给手机处理，避开此前板端反复出现的 TLS connection reset。实物测试中 UDP 发送在短暂正常后反复出现 `ENOMEM` / `errno=12`；降低发送速率、切换广播及静态 Wi-Fi 缓冲均未证明能解决，因此最终优先使用 TCP 的流量控制。该错误来自发送路径，不能仅据此认定整个应用内存耗尽，也尚未确定驱动内部的确切根因。

TCP 连接目标为热点网关 `19422`，连接探测最多 350 ms、失败后最多每 5 秒重试；探测失败才向 UDP `19421` 发送。两种传输使用相同的 JCU1 加密分片。TCP 每帧最多 800 ms，发送后等待手机的完整帧确认，成功后才发送下一帧。超时关闭旧连接、归还帧缓冲，下一轮取新图；不建立多帧 TCP 应用发送队列。确认只代表手机完成重组，云端上传结果仍以 App 及服务器状态为准。

## 升级与开启

1. 安装 v0.2.0 APK，覆盖安装可保留服务器连接配置。
2. 将 ESP32 升级到 v0.2.0。已使用本项目 v0.1.0、相同分区布局时，推荐解压固件 ZIP 后运行 `./flash_windows.ps1 -Port COM11 -ApplicationOnly`，只写应用，保留 NVS 中的热点及连接配置。首次烧录按 FLASHING.md 操作。端口应以实际设备为准。
3. 按一下 RESET，BOOT 保持松开。新固件在没有保存过传输方式时默认手机中转；它从热点 DHCP 网关取得手机接收地址，不用手填手机 IP。首次 NTP 校时可能需要几十秒。
4. 开启手机 2.4 GHz 热点，让 ESP32 连接。在 App 点击“开启摄像头中转”，允许 Jarvis 使用移动数据和后台活动。中转服务独立于语音，不需要开启麦克风。
5. 正常状态逐渐显示“TCP 完整帧 … · 已上传 … 帧”或 UDP 回退状态，服务器摄像头状态显示在线。收到完整帧但上传失败表示手机至服务器的网络仍需排查。云端较慢时，手机会跳过中间帧、上传最新图，因此两个计数不要求相等。

如果摄像头以前保存了 HTTPS 模式，按住 BOOT 约 3 秒打开配网窗口，进入摄像头配网页面选择手机中转；或者使用新版 App 配网时勾选“摄像头通过手机中转”。若需回到 ESP32 直接上传，在同一位置选择 HTTPS。为兼容已安装的中间版本，NVS 和配网协议仍使用 `transport=udp` 表示自动 TCP / UDP 中转。旧 APK 配网仍可用，会明确选择 HTTPS。

修改服务器、密钥或会话后，先“保存并检查连接”，再重新开启摄像头中转。手机和摄像头的密钥、会话 ID 必须一致。中转不会保存摄像头照片到磁盘；测试也不自动上传用户照片为公开附件。

## 旧画面与内存上限

| 所在位置 | 策略 |
|---|---|
| ESP32 摄像头驱动 | 使用固定数量的帧缓冲复用；取得帧后所有退出路径都归还缓冲。驱动缓冲归还后可被下一帧覆盖，不在每帧调用 malloc/free 重建 DMA 缓冲 |
| ESP32 中转发送 | 每帧最多 256 KiB；分片发送及 TCP 等待确认预算 800 ms，发送结束即归还帧缓冲；不重发旧图，不建发送队列；获取到的画面若已超过 1.5 秒则丢弃 |
| 手机分片重组 | TCP / UDP 共用一个受锁保护的最新帧重组缓冲，最多 256 KiB；新帧覆盖未完成旧帧，缺片超过 1 秒主动释放；重复、损坏、错误密钥和过期包丢弃。TCP 另有 1176 字节包缓冲，不完整包超过 1 秒关闭连接；检查周期 250 ms |
| 手机上传 | 一个正在上传的帧加一个最新待发帧；替换待发帧立即解除旧引用，待发帧超过 2 秒释放，不重试旧图；正在传输的请求最多 6 秒，结束后解除其图像引用 |
| 服务器缓存 | 每会话只保留最新图；替换时立即 close 旧 PIL 图像，超过 4 秒由 250 ms 周期后台任务 close；最多 32 个会话元数据，不保留过期像素 |
| 模型取帧副本 | 只在推理使用期间保留，推理完成后 close；不能在 GPU 仍使用该帧时提前释放 |

手机的 Java 大字节数组解除引用后，由运行时 GC 回收，不调用 `System.gc()` 强制回收每一帧。服务器的 PIL 图像主动 `close()`。操作系统与 Python 内存分配器可能保留空闲页供复用，因此 RSS 不一定立即下降。模型的 KV/视觉上下文按既有滑动窗口管理，这与原始 JPEG/PIL 帧缓存不同；此改动不会每帧清空 GPU 缓存或强制让模型忘记整段对话。

## JCU1 数据报格式

所有整数大端序。40 字节明文头作为 AES-GCM AAD，随后是密文与 16 字节 tag。每个 JCU1 包最多 1176 字节，UDP 避免通常 1500 字节 MTU 下的 IP 分片。TCP 则在每个相同加密包前附加 2 字节大端包长度（56–1176），接收端不依赖 TCP 的读边界。完整帧认证重组成功后，手机回传 8 字节 `JCA1` + 4 字节大端帧序号；这个确认不是云端接收凭证。

| 偏移 | 长度 | 内容 |
|---|---:|---|
| 0 | 4 | ASCII `JCU1` |
| 4 | 12 | 本次摄像头启动的随机 ID |
| 16 | 4 | 帧序号，溢出前更换随机 ID |
| 20 | 4 | JPEG 总字节数，最大 262144 |
| 24 | 2 | 分片索引，从 0 开始 |
| 26 | 2 | 分片数，每片明文最多 1120 字节 |
| 28 | 8 | 捕获时刻 Unix 毫秒 |
| 36 | 4 | 保留位，当前为 0 |
| 40 | ≤1120 | AES-256-GCM 密文 |
| 其后 | 16 | GCM tag |

密钥为 `SHA256(UTF8("jarvis-camera-udp-v1\n" + session + "\n" + token))`，nonce 为头部 SHA256 的前 12 字节。启动随机 ID、帧序号和片号共同保证正常发送下 nonce 不重复；不对同一个帧/片号重新加密不同内容。接收端先验证 tag 再分配整帧内存。访问 token 本身不在 UDP 包中传输。

依赖手机自动时间与 ESP32 NTP：接收端拒绝超过 4 秒或未来超过 5 秒的时间戳，服务器也根据 `X-Frame-Captured-At-Ms` 拒绝迟到旧帧。有限时间窗与序号检查用于限制重复包；不是跨 App 重启持久化的绝对防重放协议。

## 当前验证边界

自动化覆盖乱序重组、丢片超时、只保留最新帧、重复/旧帧拒绝、错误密钥、篡改检测、TCP 粘包/拆包/长度边界/不完整包绝对超时，以及服务器无新请求时自动释放旧图。固件和 APK 均实际编译检查。真实 OPPO 上通过 ADB 转发向 TCP 接收服务发送 15 张约 22 KB 合成 JPEG，15 张均返回确认、服务器实际收到其中 10 张新图；这独立验证 App 至云端链路，不等于 ESP32 热点链路验收。实物持续传输结果单独记录在 [VALIDATION.md](VALIDATION.md)。
